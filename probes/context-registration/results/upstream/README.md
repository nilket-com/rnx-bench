# Upstream source check before proposing a startup optimization

Checked 2026-09-13 against `rune-rs/rune` main at
`bb8e69372353c50e271c9f115bc771c77aa6b83e`, resolved with
`git ls-remote https://github.com/rune-rs/rune.git HEAD refs/heads/main`.
This is a **source comparison**, not a benchmark of main.

## Result

Eager per-implementing-type trait expansion remains in main. The three
profiled source files have changed since the published Rune 0.14.2 crate, but
the relevant registration mechanism remains:

- `Context::install` still loops through a module's trait implementations.
- `install_trait_impl` still invokes the handler with a type-specific
  `TraitContext`. Its only textual change is `handler(...)` becoming
  `handler.call(...)`.
- `install_associated` still clones type information, constructs named paths,
  registers function aliases and constants, and installs metadata. Its only
  textual change is constructing `ConstValueBuf` with a fallible conversion
  instead of `ConstValue`.
- `install_meta` is byte-for-byte identical between the two files.

These observations support investigating the mechanism upstream. They do
not establish that main has the same timings or allocations as 0.14.2.
Among other changes, main has a different function-handler representation,
a different Arc implementation, and an additional default f64 constants
module. The 0.719 ms measurement belongs to 0.14.2.

## Constraint on sharing handlers

The description "the underlying closure is the same for every type" needs
qualification. In both versions, the Iterator trait handler looks up the
implementing type's `NEXT` protocol handler and wraps it in a `Caller`.
Methods such as `count` and `fold` capture that caller by value. The closure
body is shared code, but the captured function handler is type-specific.

Sharing one stateful handler across all types would require redesigning how
that state is supplied or dispatched. The current design resolves that
handler during registration; a proposal should assess whether reduced
startup work introduces additional runtime lookup or dispatch. This check
does not quantify that tradeoff.

Main replaces `Arc<FunctionHandler>` with a `FunctionHandler` wrapper
generated by `declare_dyn_fn!`. The wrapper's `new` still calls
`Arc::try_new(f)`; it is not evidence that all handler allocations disappeared.

Likewise, the function-map entry count and metadata record count describe
overlapping work. They cannot be treated as independent operations to derive
a uniform "half a microsecond per entry" cost.

## Relevant history and search coverage

- [Issue #671](https://github.com/rune-rs/rune/issues/671), open when checked,
  describes the move to protocol-based iterator types and explicitly discusses
  filling in default methods during context construction to support efficient
  dispatch.
- [PR #774](https://github.com/rune-rs/rune/pull/774) introduced an initial
  implementation of traits and was merged in 2024.

GitHub issue/PR searches were run for `context performance`, `startup`,
`default trait`, and `with_default_modules`, scoped to this repository.
Exact queries, counts, and result URLs are in `check.json`; response snapshots
are in `search-*.json`. No matching startup-registration performance report
was identified in these searches. This is bounded search coverage, not proof
that no related discussion exists.
